## 1. 设计原则

| 原则 | 具体做法 | 为什么 |
|---|---|---|
| **以任务书为准** | 架构覆盖任务书全部路线：标定和自标定 → 传统匹配 → 学习方法 → 难测场景处理 → 体积计算 → 板上部署 → 对比评测 | 考核按任务书来。各部分按阶段逐步开放，不一次全做 |
| **电脑和板子分两层** | 电脑上用 Python 研究算法、准备数据、打分；板子上用 C 语言，只实现已经定稿的算法 | 电脑上调试快、工具多；板子上资源紧，适合"翻译"，不适合做研究 |
| **板子版必须能和电脑版对答案** | 电脑版给出"标准输出"，板子版逐项比对 | 否则板子上结果不对时，分不清是算法问题还是移植问题 |
| **预算从一开始就算清楚** | 每帧 ≤1200 万次乘加、内存 ≤200 KB、程序 ≤300 KB、≥5 fps，从第一天就约束算法选择 | 到最后再压缩，往往要推倒重来 |
| **出题、答题、判卷分开** | B 准备数据和标准答案，A、C 写算法，D 独立打分 | 避免自己出题自己考 |
| **失败要看得见** | 无效点填 NaN 并附掩膜；"测不了"和失败都写进报表；样本不删 | 掩盖失败的系统，实际使用时会出大问题 |

## 2. 数据怎么流动

```
                    ┌─────────── B：数据 ───────────┐
  公开数据集 ──┐    │                                │
  虚拟烤箱渲染 ┼──▶ │  输入包（左右图 + 标定）        │
  台架实拍 ────┘    │  答案包（真实距离 + 有效掩膜） ─┼──────────────────┐
                    └───────────┬────────────────────┘                  │
                                ▼                                       │
          A：标定与校正 —— 把左右图"摆正"；监测摄像头是否变歪             │
                                ▼                                       │
          C：深度算法 —— 找对应点 → 视差 → 距离；标出不可信区域；          │
                         判断镜头是否脏了                                │
                                ▼                                       │
          A：几何 —— 距离 → 三维点 → 找托盘 → 高度地图 → 厚度、体积       │
                                ▼                                       ▼
          D：打分 —— 距离误差、覆盖率、厚度/体积误差  ◀────────── 标准答案
                                ▼
          报告：困难条件成绩表、精度-计算量对比、三联对比表

  板子线：C 交出定稿算法的整数版和标准输出，并写板上匹配程序；
          A 搭板上框架，移植校正和几何部分，集成后实测速度和内存
  对标线：B 调研结构光/ToF 参数，核算成本和功耗，汇编三联对比表
```

两条关键规则：

- **答案包永远不进入算法。** 只有 D 的打分程序会读答案包。
- **每一段都有固定的输入输出格式**（见[共同约定与接口](ai/00_共同约定与接口.md)第 5 节）。只要格式对，任何一段都可以单独替换、单独测试。

## 3. 板子上的程序长什么样（目标形态）

```
 ① 采集        两个摄像头同时拍 320×240
     ↓
 ② 校正+缩小   按预先算好的映射表把图"摆正"，并缩到 160×120（查表，几乎不耗算力）
     ↓
 ③ 匹配        逐行处理，不把所有中间结果都存下来（省内存）
     ↓
 ④ 细化        亚像素细化 + 左右互相校验 + 可信度评分
     ↓
 ⑤ 距离        视差 → 距离
     ↓
 ⑥ 几何        高度地图 → 厚度、体积
     ↓
 ⑦ 输出        结果 + 状态（正常 / 空 / 测不了）+ 健康提示

 后台低频检查（不占每帧预算）：摄像头有没有偏（自标定）、镜头有没有脏（污染提示）
```

**两种运行模式：**

| 模式 | 要求 | 什么时候用 |
|---|---|---|
| 连续模式 | 每秒 ≥5 次，每次 ≤1200 万次乘加 | 首选 |
| 单次模式 | 放入食物、关门后算一次，1 秒内出结果 | 算力不够时的退路（任务书风险 2 允许）。报告里要注明用的是哪种模式 |

## 4. 算力和内存账

> 以下数字基于**假设参数**：
> - 两个摄像头间距 7 cm；
> - 水平视角约 70°，对应焦距约 228 像素（320 宽）或约 114 像素（160 宽）。
>
> 第 2 周选定模组后，由 A 用真实参数重算；结论不同时，以重算结果为准。

### 4.1 精度账：视差要多准

| 距离 | 视差（160×120 下） | 要做到 5% 误差，视差最多能错多少 |
|---|---|---|
| 0.3 m | 约 26.6 像素 | 约 1.33 像素 |
| 1.0 m | 约 8.0 像素 | **约 0.40 像素**（任务书主指标） |
| 1.5 m | 约 5.3 像素 | 约 0.53 像素（这一档允许 10% 误差） |

**结论：** 1 米处要求视差误差小于半个像素，所以**亚像素细化是核心工作**，不是可有可无的优化。C-02 会在第 5 周前验证能否做到。

### 4.2 计算量账

- **每个像素的预算：** 每帧 1200 万次乘加，160×120 = 19200 个像素，平均每个像素约 **625 次**。
- **每个候选视差的预算：** 视差搜索范围约 32（足以覆盖 0.3–1.5 m），所以每个候选视差只能分到约 **20 次**运算。
- **作为对比：** 一层最小的卷积神经网络（3×3 卷积，8 通道进、8 通道出），在 160×120 上就要约 1100 万次。

**结论：**

- 板子上不可能跑像样的神经网络。
- "学习方法"在板子上只能是极轻量的后处理，比如对传统算法的结果做细化或补洞。
- 大模型只在电脑上用，看看"最好能做到多好"。

### 4.3 内存账

- **代价表太大：** 如果把所有候选视差的匹配代价都存下来，160 × 120 × 32 ≈ 61 万个数，按每个 1 字节算约 **600 KB**，是 200 KB 预算的 3 倍。所以匹配必须**逐行处理、边算边丢**，不能一次存下整张代价表。
- **图像本身也占内存：** 两张 320×240 的灰度图就要约 150 KB。"内存 ≤200 KB"算不算这两张图，直接决定方案是否可行，必须在开题时定下来。

## 6. 模块之间的关系

```
contracts（接口）
   ↑ 所有模块都只依赖它
data / synthetic / calibration / stereo / geometry
   ↑
pipeline（运行命令）←── evaluation（打分）
```

| 设计 | 为什么 |
|---|---|
| 模块之间只通过 `contracts` 里定义的数据结构交换数据，不直接调用对方的内部函数 | 别人改了内部实现，也不会影响你；每一段都能单独测试 |
| `evaluation` 不能调用 `stereo`、`geometry` 的代码 | 打分要独立，不能用被测程序来检验被测程序 |
| `edge/` 不依赖任何 Python 代码 | 板子上没有 Python；两边靠"标准输出"文件对答案 |

## 7. 每项指标谁负责、谁来量

| 任务书指标 | 谁负责做到 | 谁来测/核对 | 备注 |
|---|---|---|---|
| 距离误差：0.3–1.0 m 中位数 ≤5%、95 分位 ≤10%；1.0–1.5 m 中位数 ≤10% | C | D 独立打分，B 提供标准答案 | 按距离分档；每个场景权重相同 |
| 有效覆盖率：普通场景 ≥85%，难测场景 ≥60% | C | D | 分母是"标准答案有效的点"；失败区域比例另报 |
| 规则物体积/厚度误差 ≤10% | A | D 打分，B 提供卡尺/参照物真值 | |
| 标定误差 ≤0.5 像素，能自动校正 | A | B 用没参与标定的图复核 | |
| 0–70 °C 精度下降 ≤20% | A（温漂修正） | B 提供温箱，D 打分 | |
| 镜头油污时覆盖率下降 ≤20 个百分点，并给出提醒 | C | B 提供油污窗，D 打分 | |
| ≥5 fps、≤1200 万次乘加/帧、内存 ≤200 KB、程序 ≤300 KB | A（板上集成实测） | C 负责算法本身守预算 | 必须是板子实测，电脑数据不算 |
| 功耗 ≤1.5 W；成本比结构光/ToF 低 ≥40% | B | B 汇入对比表 | 计算方法开题时定 |
| 仿真 ≥3000 对、实拍 ≥500 对、抽查 ≥10% | B | D 阶段复跑时核对清单 | |
| het-ai 规范：参数写配置、多目标对比、先 dry-run | C（参数搜索、对比）、D（dry-run） | D 阶段复跑时检查 dry-run 记录 | 不自建实验平台 |

## 8. 开题时必须定下来的事

| 事项 | 为什么必须早定 | 谁提出 |
|---|---|---|
| 模组型号、两个摄像头的间距 | 决定视差大小和精度上限，也决定采购 | A |
| 用多大的图（160×120 还是 320×240） | 决定精度和计算量；先初定，第 5 周在决定 2 中确认 | A、C |
| 距离分档（0.3–1.0 m、1.0–1.5 m） | 打分要按档分开 | D |
| 评测协议：误差定义、覆盖率分母、多场景怎么平均、计时边界 | 必须在看到结果之前定，否则有"先射箭后画靶"之嫌 | D |
| 计算量怎么数（例如一次"差的绝对值 + 累加"算不算一次乘加） | 直接影响"≤1200 万次"是否达标 | A |
| 内存怎么算（两张图本身算不算） | 直接影响"≤200 KB"能否达标 | A |
| 成本和功耗怎么算（包含哪些部件、按多大批量） | 直接影响"便宜 40%"的结论 | B |
| 困难条件分几档、每档什么标准 | 仿真和实拍都要按这个准备数据 | B |
| 开发集和测试集怎么划分 | 测试集一旦划定就不能改 | B |
