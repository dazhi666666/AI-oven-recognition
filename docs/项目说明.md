## 1. 一句话说清楚

**在烤箱里装两个普通摄像头，像人的两只眼睛一样，算出放进去的食物有多厚、体积多大。**

烤箱知道了这些，就能自己决定火力和时间。最后的成果是一套"双目深度模组"的参考方案，包括摄像头、算法和跑在烤箱主控芯片上的程序。

---

## 2. 为什么要做

**烤箱想要"智能控温"，就得知道食物多大。** 一块 2 cm 厚的牛排和一块 5 cm 厚的牛排，需要的加热方式完全不同。

**现有的测距方案在烤箱里不好用：**

| 方案 | 原理 | 在烤箱里的问题 |
|---|---|---|
| 结构光 | 往物体上投射图案，看图案变形 | 投射器怕高温，玻璃窗一脏就失效；贵 |
| ToF（飞行时间） | 发出光，测光飞回来的时间 | 同样有发光部件，怕高温、怕油污；贵 |
| **双目（本项目）** | 两个普通摄像头，像人眼一样看 | 没有发光部件，便宜；**难点全在算法上** |

**谁需要它：** 家电厂商。厨电对成本非常敏感，一个零件省几块钱，乘上百万台就是大钱。任务书要求我们的物料成本比结构光/ToF 方案至少低 40%。

---

## 3. 原理：两只眼睛怎么算距离

伸出一根手指放在眼前，轮流闭上左眼和右眼，手指看起来会左右"跳动"。手指离眼睛越近，跳得越厉害。这个"跳动的距离"就叫**视差**。

两个摄像头也是一样：同一个点在左图和右图里的位置会差几个像素。

```
距离 = 焦距 × 两个摄像头的间距 ÷ 视差
```

**用实际数字感受一下。** 假设两个摄像头相距 7 cm，图像宽 160 像素：

| 物体距离 | 左右图里差多少像素（视差） | 视差估错半个像素，距离会错多少 |
|---|---|---|
| 0.3 m | 约 27 像素 | 约 2% |
| 1.0 m | 约 8 像素 | 约 6% |
| 1.5 m | 约 5 像素 | 约 9% |

**这张表就是本项目最核心的难点：**

- 任务书要求 1 米处误差不超过 5%，也就是说视差要估得比**半个像素还准**（约 0.4 像素）。
- 而我们的图像只有 160×120，比手机照片小几百倍。

所以"把视差估准到零点几个像素"（行话叫**亚像素精度**）是整个项目的重中之重。

## 4. 要做到什么程度（验收指标翻译成白话）

| 任务书原文 | 白话解释 |
|---|---|
| 0.3–1.0 m 深度相对误差中位数 ≤5%，95 分位 ≤10% | 物体在 1 米处时，一半以上的点误差不超过 5 cm；绝大多数点误差不超过 10 cm |
| 1.0–1.5 m 中位数 ≤10% | 远一点的地方可以放宽到 10% |
| 普通场景有效覆盖率 ≥85% | 100 个本该能测到的点里，至少 85 个要给出距离。测不出来可以留空，但不能乱填 |
| 弱纹理/高光/透明场景 ≥60% | 白面团、反光的金属盘、保鲜膜这类难测的东西，至少测出 60%，测不出的地方要明确标出来 |
| 规则物体积/厚度误差 ≤10% | 放一个 120 mL 的方块进去，测出来要在 108–132 mL 之间 |
| 深度帧率 ≥5 fps | 每 0.2 秒出一张深度图 |
| 单帧 ≤12 MMAC | 每张图最多做 1200 万次乘加。听起来很多，但平均到每个像素只有约 600 次；再分到 32 个候选视差上，每个候选只能算约 20 次 |
| SRAM 峰值 ≤200 KB | 程序运行时最多占用 200 KB 内存。一张 320×240 的灰度图就要 75 KB，左右两张就是 150 KB |
| 算法代码 + 常量 ≤300 KB Flash | 整个程序加上参数，大小不能超过 300 KB |
| 重投影误差 ≤0.5 像素 | 摄像头标定要准到半个像素以内 |
| 0–70 °C 精度衰减 ≤20% | 机器从冷到热，精度最多变差 20%。比如原来 5%，最多变成 6% |
| 油污视窗下覆盖率下降 ≤20 个百分点，并给出污染提示 | 镜头脏了，能测的点最多少 20%，并且要能提醒用户"该擦玻璃了" |
| 模组功耗 ≤1.5 W | 两个摄像头加处理，总功耗不超过 1.5 瓦 |
| BOM 相对结构光/ToF 下降 ≥40% | 物料成本至少便宜四成 |

**算力有多紧？** 主控芯片 RK3506 是一颗三核 ARM Cortex-A7，没有 AI 加速芯片，算力大约相当于十几年前的智能手机。任何"跑个大神经网络"的想法在板子上都行不通。

## 5. 难在哪里

1. **图小、算力小，还要求准。** 第 3 节已经说过，要在 160×120 的小图上把视差估准到零点几个像素，而每个像素只能分到几百次计算。
2. **烤箱里的东西很难"看"。**
   - **没有花纹**：面团、白色的鱼片。左右图里找不到能对上的特征点。
   - **反光**：金属烤盘、油亮的表面。左右两个摄像头看到的高光位置不一样，会被误认成不同的点。
   - **透明**：玻璃碗、保鲜膜。看到的其实是后面的东西。
3. **环境恶劣。** 灯光偏黄偏暗，有蒸汽，玻璃窗上有油污。
4. **便宜的模组不稳定。** 两个摄像头装得稍有偏差、受热后轻微变形，都会直接变成测距误差。所以需要"运行时自己发现偏差、自己校正"（**自标定**）。

## 6. 整个系统怎么工作

```
 ① 拍照        左右两个摄像头同时拍一张（320×240）
     ↓
 ② 校正        把两张图"摆正"：让同一个点在左右图里处于同一行，并缩小到 160×120
     ↓
 ③ 找对应点    对左图每个像素，在右图同一行找最像的位置，得到视差（C 负责的核心）
     ↓
 ④ 判断可信度  哪些点算得靠谱，哪些点不靠谱（反光、无纹理）要标出来，不能乱填
     ↓
 ⑤ 换算距离    视差 → 每个点离摄像头多远
     ↓
 ⑥ 找托盘      找出食物下面那个平面（烤盘）
     ↓
 ⑦ 算高度      每个点比烤盘高多少 → 得到一张"高度地图"
     ↓
 ⑧ 算体积      把高度地图上每一小格的"高度 × 面积"加起来 → 体积；最高点 → 厚度
     ↓
 ⑨ 输出        厚度、体积，以及"测得了 / 测不了 / 里面是空的"的状态

 旁路检查：摄像头是不是歪了（自动校正）；镜头是不是脏了（提醒擦拭）
```

**两种运行方式：**

- **连续模式**：每秒出 5 次结果，理想情况。
- **单次模式**：放进食物、关上门后算一次，1 秒内出结果。任务书允许算力不够时退到这个方案。

## 7. 我们的总体策略

| 原则 | 意思 | 为什么 |
|---|---|---|
| **先在电脑上做对，再搬到板子上** | 所有算法先用 Python 在电脑上实现和测试，确定了再用 C 语言移植到 RK3506 | 电脑上调试快；板子上只做"翻译"，不做研究 |
| **先简单方法，再复杂方法** | 先用现成的传统算法（OpenCV 的 SGBM）做出能用的版本，再考虑加学习方法 | 先有一个能比较的基准，后面才知道改进有没有用 |
| **先打通，再做好** | 第 5 周左右要用仿真数据跑通"拍照 → 体积"的全过程，哪怕误差很大 | 越早接起来，越早发现各部分对不上的问题 |
| **最怕的事最先试** | 精度够不够、算力够不够、采购来不来得及，都在前 5 周验证 | 如果方向不对，越早知道越好，有时间换方案 |
| **数据由专人独立准备** | 做算法的人不给自己出测试题 | 自己出题自己考，分数没有说服力 |

## 8. 数据从哪里来

我们需要大量"左右图 + 每个点的真实距离"来训练和检验算法。数据有三种来源，各有用途：

| 来源 | 是什么 | 用来干什么 | 局限 |
|---|---|---|---|
| **公开数据集**（Middlebury） | 学术界公认的双目测试图，附带精确的真实视差 | 检查程序有没有写错，比如单位、方向、编码 | 拍的不是烤箱，距离和分辨率都对不上 |
| **仿真**（用 3D 软件渲染虚拟烤箱） | 在电脑里搭一个烤箱、放上虚拟食物，渲染出左右图，真实距离是精确已知的 | 大量、可控地生成各种情况：不同材质、距离、光照、反光、蒸汽、油污 | 再逼真也不是真实世界，有"仿真到现实"的差距 |
| **实拍** | 自己搭台架，用真实模组拍；用卡尺和已知尺寸的参照物测真值 | 最终证明在真实世界里能用 | 慢、费人工，真值不如仿真精确 |

**数量要求**（来自任务书）：仿真 ≥3000 对，实拍 ≥500 对，至少抽查 10% 的数据质量。

**退化矩阵**：专门准备 4 类"困难条件"的数据（暗光/偏色、蒸汽、镜头油污、透明/反光物体），每类分几个等级，看算法在每种条件下表现如何。

## 9. 四个人怎么分工

分工按"谁和什么东西打交道"来划分：A 管相机，B 管数据和硬件，C 管核心算法，D 管打分。大家在同一个工作区里干活，分工只是说明"这件事主要由谁推进"，不是划地盘，需要时互相改代码都没问题。

### A：标定、几何与端侧 —— "相机这一头"

- **主要推进：**
  - 选摄像头模组，算清楚间距和视角怎么定；
  - 摸清 RK3506 的算力；
  - 标定摄像头，做"摆正"图像的校正；
  - 运行时发现摄像头歪了能自动校正；
  - 从距离算出厚度和体积；
  - 把程序搬到 RK3506 板子上，并实测速度、内存。
- **交出什么：** 选型报告、标定流程、厚度/体积程序、板上能跑的演示。

### B：数据与硬件 —— "数据和物料这一头"

- **主要推进：**
  - 公开数据整理；
  - 做仿真（虚拟烤箱）；
  - 搭拍摄台架，实拍并测量真值；
  - 准备各种困难条件的数据；
  - 数据质量抽查；
  - 调查结构光/ToF 的公开参数，核算成本和功耗；
  - 搭温箱、油污窗等环境测试台；
  - 最后汇编"三联对比表"（精度/成本/功耗对比）。
- **交出什么：** 一套套"左右图 + 标定 + 真值"的数据包，以及对比表和成本报告。

### C：深度算法 —— "核心算法"

- **主要推进：**
  - 找对应点（匹配）；
  - 把视差估准到零点几个像素；
  - 判断哪些点可信；
  - 在算力限制内加入轻量的学习方法；
  - 处理无纹理/反光/透明；
  - 镜头脏了能检测出来；
  - 自己做参数对比实验；
  - 写板子上跑的匹配核心代码。
- **交出什么：** 视差图、距离图、可信区域；各方案"精度 vs 计算量"的对比表；板上的匹配程序。

### D：集成与评测—— "独立打分"

- **主要推进：**
  - 制定"怎么算分"的规则（评测协议）；
  - 写独立的打分程序；
  - 写一个最简单的运行命令；
  - 每个阶段末独立复跑一次，确认数字是真的。
- **交出什么：** 评测协议、打分程序、运行命令、每阶段的评测结论、最终评测报告。

## 10. 怎么证明我们真的做到了

**打分的人和做算法的人分开。** C 自己测出误差 4% 后，D 再用独立写的打分程序，在 B 准备的测试数据上跑一遍确认。

**结论要分层，不能混着说：**

| 层级 | 意思 | 例子 |
|---|---|---|
| 程序跑通 | 能运行、不报错 | "SGBM 能输出视差图" |
| 理想用例通过 | 在人为构造的完美输入上结果正确 | "给一个标准方块的高度图，算出 120 mL" |
| 公开数据表现好 | 在 Middlebury 上误差小 | "公开场景误差 3%" |
| 仿真达标 | 在虚拟烤箱里达标 | "仿真 1 米处误差 4.5%" |
| 实物达标 | 在真实台架上达标 | "实拍 1 米处误差 4.8%" |
| 端侧达标 | 在 RK3506 板子上达标 | "板上 5.2 fps、误差 4.8%" |

"电脑上跑得快"不等于"板子上能到 5 fps"，"仿真里达标"也不等于"实物达标"，汇报时顺带说一句是哪一层。

## 11. 几条底线

只有这几条是硬性的，违反了，结果就不可信：

1. **不编造。** 没有真值就说没有，不拿算法自己的输出当答案。
2. **算法不看答案。** 算法运行时不读标准答案。
3. **测不出就标无效。** 测不出来的点标成"无效"，不填 0 冒充。
4. **失败样本不删。** 测不准的样本也留在结果里。

其他的事大家商量着办，详见[共同约定与接口](ai/00_共同约定与接口.md)。

## 13. 术语表

| 术语 | 白话 |
|---|---|
| 双目 / 立体视觉 | 用两个摄像头像人眼一样测距离 |
| 视差 | 同一个点在左右图里位置差了多少像素 |
| 亚像素 | 比一个像素更细的精度，比如 0.3 像素 |
| 基线 | 两个摄像头之间的距离，本项目定在 6–8 cm |
| 标定 | 测出摄像头的精确参数（焦距、镜头畸变、两个摄像头的相对位置） |
| 校正 | 根据标定结果把左右图"摆正"，让对应点在同一行上 |
| 自标定 | 机器运行时自己发现摄像头偏了，自己修正 |
| 重投影误差 | 衡量标定准不准的指标，越小越好 |
| SGBM | OpenCV 里一个常用的传统匹配算法 |
| 弱纹理 | 表面没什么花纹，比如白面团 |
| 覆盖率 | 能给出距离的点占所有应测点的比例 |
| 真值 | 标准答案，比如仿真里精确已知的距离、卡尺量出来的尺寸 |
| 退化矩阵 | 按困难条件（暗光、蒸汽、油污、反光/透明）和程度分好类的测试集合 |
| 仿真 | 用电脑渲染虚拟烤箱和食物，生成测试图片 |
| 端侧 / 板端 | 程序跑在烤箱的主控芯片（RK3506）上，而不是电脑上 |
| MMAC | 百万次乘加运算，衡量计算量的单位 |
| SRAM / Flash | 运行时占用的内存 / 存放程序的空间 |
| fps | 每秒出几次结果 |
| 定点 | 用整数代替小数做计算，在小芯片上更快 |
| 黄金向量 | 电脑版程序的标准输出，用来检查板子版程序算得是否一模一样 |
| BOM | 物料清单和成本 |
| 三联表 | 本方案与结构光/ToF 在精度、成本、功耗三方面的对比表 |
| 阶段检查 | 每个阶段结束时，D 统一跑一遍出成绩表 |
| dry-run | 只检查配置和数据对不对，不真正运行算法，用来提前发现低级错误 |
| het-ai | 公司的模型开发规范：参数写在配置文件里、先 dry-run 再正式运行 |
